## Как связаны данные и интерфейс

`tokens.json`, `system.json`, контракты и профиль остаются авторскими источниками с разными обязанностями. Профиль выбирает конфигурацию и связывает recipes; система определяет пресеты; токены задают роли; контракты описывают допустимые свойства, состояния и способы проверки.

Во время сборки compiler разрешает эти связи. `createWebBindings` переводит результат в CSS-переменные и диагностические записи. React получает значения через этот адаптер, а live props — через `bindWebRecipe` и существующую модель формы. В адаптере нет Node-зависимостей. Числовые foundation-значения получают `px` только на границе web; размеры должны быть конечными и допустимыми для своей роли. Отрицательный letter-spacing допустим, отрицательные высоты, радиусы или промежутки отклоняются.

Адаптер также явно владеет DOM ids, refs, служебными data-атрибутами, `style` и отдельными маршрутами событий. Попытка записать конфликтующее свойство в recipe даёт `PROFILE_ADAPTER_PROP_CONFLICT`. Неподдерживаемая пара `$handler` и свойства даёт `PROFILE_HOST_HANDLER_UNSUPPORTED`. Авторское значение не заменяется незаметно при рендере.

В текущей версии каталог создаётся **при сборке**. Переключатели страницы выбирают одну из восьми конфигураций. После изменения токенов, пресетов, контракта или профиля требуется повторный `npm run build`. Доступна плотность `regular`.

## Измеренная геометрия

Значения ниже измерены в реальном браузере после загрузки Inter. Высота относится к control box, включая границу; текст и line-height — к размерному пресету. Результаты одинаковы в Light и Dark.

| Размер | Высота Button / IconButton / TextField | Радиус | Текст / строка | Padding-inline Button |
| --- | --- | --- | --- | --- |
| s | 24 px | 6 px | 12 / 16 px | 8 px |
| m | 32 px | 8 px | 14 / 20 px | 12 px |
| l | 40 px | 10 px | 16 / 24 px | 16 px |
| xl | 48 px | 12 px | 18 / 28 px | 20 px |

Во всех восьми конфигурациях промежуток от блока поля до строки действий составляет **24 px**, между Save и Cancel — **12 px**. Это измеренные расстояния между блоками, а не только прочитанные значения CSS-переменных.

Для Button размера `m` проверенные ширины до и во время loading: **127 → 127 px** без иконки и с левой иконкой; **151 → 151 px** с правой и с обеими иконками. Проверка также сравнивает положение label, размер spinner и сохранение фокуса. Для layouts без ведущей иконки web-адаптер заранее резервирует slot; это условие входит в область подтверждения.

## Поведение формы и найденные дефекты

Required-проверка использует строку с удалёнными краевыми пробелами для решения о валидности, сохраняя исходный ввод. После первого показа ошибки изменение значения повторно проверяется. При невалидном submit модель возвращает фокус в input.

Браузерная проверка обнаружила проблему последовательности событий: появление ошибки на blur сдвигало Save между нажатием и отпусканием указателя. Первый click терялся. Теперь блок поля заранее резервирует одну строку сообщения; минимальная высота выводится из разрешённых размеров подписи, контрола, промежутков и сообщения. Проверка использует **одно настоящее нажатие**, без повторной попытки.

Во время сохранения синхронный guard владельца формы блокирует повторную отправку по click, Enter и программному `requestSubmit()`. Save сохраняет фокус и показывает loading. Input остаётся редактируемым. Ответ на snapshot A фиксирует A как сохранённое значение и оставляет более новое B в поле как несохранённую правку. Ошибка запроса относится к форме; retry отправляет текущее значение. Cancel возвращает последнюю сохранённую версию.

Для TextField действует решение D22: native `disabled` подавляет error presentation и `aria-invalid`; ошибка может оставаться в состоянии владельца. При обычном error клавиатурный фокус отображается независимо. Внешние и локальные `aria-describedby` объединяются без дубликатов и ссылок на отсутствующее локальное сообщение.

Справка использует клавиатурно доступную IconButton, видимое пояснение и `aria-expanded`. Этот сценарий не заявляет полноценный Tooltip или persistent selection.

## Воспроизведение

Из корня checkout с третьим этапом:

```bash
npm --prefix packages/seda-contracts ci
npm --prefix packages/seda-contracts run validate
npm --prefix packages/seda-contracts run audit
npm --prefix packages/seda-contracts test
cd portal/component-lab/pilots/settings-parametric
npm ci
npx playwright install chromium
npm run typecheck
npm run build
npm run serve
```

Открыть **http://127.0.0.1:5184/**. Во втором терминале из папки пилота выполнить `npm run verify`. При использовании отдельного каталога браузеров передать одинаковый `PLAYWRIGHT_BROWSERS_PATH` при установке и проверке.

Verifier создаёт `.diagnostics/verification.json`, `settings-light-m.png`, `settings-dark-m.png` и `settings-error-focus.png`. Сгенерированные результаты, `dist/` и зависимости исключены из Git; публикуются исходный verifier и этот краткий отчёт. Скриншоты просмотрены для визуальной проверки и не заменяют измерение DOM.

## Граница результата и следующий этап

Подтверждён один React-пилот с тремя типами компонентов, восемью профилями и локальной имитацией транспорта. Это рабочий вертикальный срез от авторских правил до браузера. Публичная библиотека получила перечисленные исправления, но остальные компоненты и все визуальные варианты не проходили такую матрицу.

Отдельной работы требуют Firefox/WebKit, touch hit areas, полный Tooltip, все шесть визуальных вариантов, uncontrolled/readonly-сценарии, многострочные сообщения, продуктовый backend и полная проверка доступности. Стабильность loading у standalone Button без ведущей иконки требует заранее зарезервированного slot; гарантия пилота не распространяется автоматически на старый способ использования. Полная миграция Figma и публикация пакета не входят в этот этап.

Следующий этап — сделать эти проверки регулярным условием изменения системы: включить воспроизводимую сборку и браузерные правила в CI, сохранять результаты как артефакты конкретного запуска и добавлять новые компоненты по той же цепочке «контракт → профиль → адаптер → измеренная проверка». Минимальные поведенческие сценарии из handoff уже исполняются; их автоматический запуск в PR и расширение окружений остаются следующей работой.
