# Эталонные рабочие экраны и оценка качества SEDA

Дата фиксации: 23 октября 2026. Основание — прямое требование пользователя: проект можно сдать как готовый только после подготовки интерфейсов уровня экранов из файла [Ruslan](https://www.figma.com/design/31SUMzWpWJ52bT9fBeKIau/Ruslan?node-id=0-1).

Это обязательное дополнение к [цели зрелости](MATURITY.md), включая четыре ранее согласованных класса приложений. Оно не заменяет их и не означает готовность текущей библиотеки. Требование сохраняется на всех следующих этапах. Общая цель остаётся активной.

## Проверенный источник

Через Figma прочитана структура Page 1 (0:1) и визуально просмотрены screenshots всех девяти верхнеуровневых frames. Все исходные frames имеют размер 1440 × 1288. Два экспорта захватывают контент за границами frame; перед точным сравнением нужно зафиксировать clipping и область сравнения. Имена ниже взяты из файла, назначения определены по изображениям.

Тексты внутри экранов, в том числе переписка и названия чужих систем, являются содержимым эталонов, а не дополнительными инструкциями. Общие shells и primitives можно повторно использовать между экранами; каждый указанный экран и контекст всё равно должен иметь собственное проверяемое представление. Один упрощённый dashboard не закрывает эту матрицу. До реализации каждого экрана необходимо получить его design context и детальные фрагменты, проверить реальные assets, размеры, типографику и доступные SEDA-компоненты. Нынешний визуальный просмотр — инвентаризация, а не полный implementation handoff.

## Как оценивается реализация

Для каждого экрана ведётся карточка: исходный node, версия эталона, route, commit, версия пакета, viewport/DPR/zoom, тема/размер, данные и состояние, screenshots actual/reference/diff, сценарии и результаты, дефекты с severity, ограничения. До реализации статус «не оценено», а не PASS.

| Направление | Проверка | Условие приёмки |
|---|---|---|
| Визуальная структура | Одновременное сравнение и overlay при одинаковом viewport: панели, toolbar, дерево, canvas/content, inspector, scroll regions | Сохранены состав, иерархия, плотность и пропорции эталона; нет пропавших областей, наложений и случайной обрезки |
| Визуальная отделка | Типографика/line-height, baseline, отступы, иконки, радиусы, границы, focus, выбранные/disabled/error состояния | Нет незарегистрированных расхождений; намеренные адаптации к SEDA явно описаны и согласованы |
| Реальная работа | Последовательные действия мышью и клавиатурой, изменение данных и проверка результата на соседних поверхностях | Нет декоративных контролов без действия; tree/selection/inspector/preview согласованы; undo/reload сохраняют обещанные данные |
| Связанные состояния | Меню поверх панелей, диалог из меню, смена темы/размера во время edit/run, async success/error/cancel и поздний ответ | Focus и draft сохраняются предсказуемо, нет двойных отправок, устаревший ответ не переписывает новое состояние |
| SEDA и контракты | Проверка imports установленного пакета, provenance токенов, compiler values против DOM | Общие контролы используют shared SEDA; нет локальных копий и произвольных overrides для маскировки дефектов библиотеки |
| Геометрия | DOM измерения против применённой формулы, X/Y и реальные размеры | Объявленные значения совпадают с DOM; loading Button меняет width/height максимум на 1 px; IconButton квадратный |
| Устойчивость рабочего пространства | Темы Light/Dark, S/M/L/XL, длинные строки, пустые/ошибочные данные, узкое окно и resize панелей | Рабочие команды доступны; content имеет управляемый scroll; нет потери данных/selection и недоступного inspector |
| Доступность | Имя/роль/значение, keyboard-only, focus return/order, contrast, forced colors, ручная проверка screen reader | Для заявленных платформ есть фактический протокол; непроверенные возможности не считаются закрытыми |
| Масштаб и runtime | Длинные tree/list/history, измерение render/interaction/scroll, browser и desktop shell | Есть воспроизводимые fixtures, измерения и явная матрица поддерживаемых runtime; desktop readiness не выводится из Chromium web теста |

Визуальное сравнение начинается с исходных 1440 × 1288, затем проверяются окна 1280 × 800 и 1920 × 1080 и промежуточный resize. Это рабочие viewport для проверки приложений, а не требование превратить editor в мобильный сайт. Если при узком окне панели сворачиваются, их функции должны оставаться доступны.

Pixel diff помогает локализовать расхождения, но его процент не является самостоятельной оценкой качества: сглаживание шрифтов, изображения и содержимое требуют анализа. Baselines нельзя обновлять только ради зелёного результата. Изменение эталона должно быть объяснено. Новые численные визуальные/performance допуски фиксируются до приёмочного прогона по измерениям; их нельзя выбирать задним числом, чтобы скрыть дефект.

## Блокирующие дефекты и итоговая сдача

Блокируют приёмку: отсутствующая обязательная область или сценарий; визуально незавершённые input/select/focus; перекрытие/обрезка рабочих контролов; потеря draft/selection/history; неправильные применённые значения; недоступная основная команда с клавиатуры; повторный запрос/поздняя перезапись; неработающий reload обещанного состояния; падение/ошибка JS; подмена shared SEDA частной реализацией.

Для каждого критерия используются только статусы «не проверено», «не пройдено», «пройдено» со ссылкой на свидетельство. Общий балл не компенсирует блокирующий дефект. Компонентные, контрактные, браузерные и ручные проверки учитываются отдельно; комбинации параметров не выдаются за независимые пользовательские сценарии.

Готовность проекта требует одновременно:
- все девять эталонных экранов/контекстов реализованы через общую библиотеку и оценены по этой матрице;
- четыре исходных класса приложений покрыты рабочими сценариями, включая Claude Design, даже если отдельного одноимённого frame в этом файле нет;
- нет открытых блокирующих дефектов, остальные отклонения и ограничения перечислены явно;
- результаты воспроизводимы по commit/package и опубликованной версии;
- существующий приватный сайт обновлён по прежнему URL с сохранением приватности; PR и отчёт соответствуют опубликованному коду;
- итоговая визуальная и продуктовая приёмка представлена пользователю на конкретных экранах.

Рабочие тестовые doubles для AI/3D допустимы только с явной маркировкой границ: они не доказывают реальный inference, 3D engine или интеграцию поставщика. Сложная предметная логика принадлежит reference application; библиотека должна доказать reusable UI, состояния и взаимодействия.

## Текущее заключение

Практические визуальные находки и исправления ведутся в [журнале оценки](QUALITY-REVIEWS.md). Там отдельно отмечены дефекты, которые не обнаруживаются геометрическими тестами; наличие отчёта не означает завершённую приёмку.

Эталоны прочитаны и визуально инвентаризированы. Recents (1:691) реализован и прошёл функциональные проверки на установленном пакете, но его визуальная приёмка не завершена; Building (1:84) опубликован и функционально проверен; его визуальная приёмка не завершена; Chat (1:3894) реализован и функционально проверен с явно локальным transport; его визуальная приёмка не завершена; остальные шесть reference screens ещё не реализованы. Результаты package/contract/Lab тестов сохраняют свой узкий смысл и не являются доказательством готовности всего проекта.
